ARCHAGENT: SCALABLE LEGACY SOFTWARE ARCHITECTURE RECOVERY WITH LLMS1. Introduction and the Problem of Architectural DriftSoftware architecture provides the foundational abstractions necessary for designing, understanding, and maintaining complex computational systems.[1] By formally defining high-level system structures, component interrelationships, and critical quality attributes—such as scalability, modularity, and maintainability—architecture serves as the definitive blueprint for software engineering teams.[1] In an ideal software development lifecycle, this architectural blueprint remains perfectly synchronized with the underlying source code, allowing engineers to reason about system behavior without needing to manually parse millions of lines of implementation logic.However, in large-scale industrial systems, this synchronization is rarely maintained. Driven by continuous requirement changes, shifting business objectives, rapid feature development, and ad hoc modifications deployed under strict deadlines, production software invariably experiences a phenomenon known as architectural drift.[1, 2] Architectural drift manifests when the implemented source code progressively diverges from the originally intended and formally documented architecture.[1] Over years or decades of active development, uncoordinated patches and localized optimizations erode the system's global structural integrity. This degradation leads to legacy software implementations that are poorly documented, excessively entangled, and profoundly difficult to recover or comprehend.[1] The resulting codebase operates essentially as a black box: the software continues to execute its required functions, but the overarching business logic, execution flows, and module boundaries are entirely obscured by structural noise.[1, 2]The recovery of accurate architectural representations from such large-scale legacy software has historically proven to be a highly resource-intensive, manual process prone to human error. Recent advances in Artificial Intelligence—specifically the rapid evolution of Large Language Models (LLMs)—have introduced unprecedented capabilities for automating code-related comprehension tasks, including source code generation, code summarization, and software vulnerability detection.[1, 3] These breakthroughs have heavily motivated researchers to explore the application of LLMs for the automated recovery of software architecture directly from source code.[1]Yet, despite their advanced semantic capabilities, existing LLM-based approaches remain severely limited when tasked with repository-level architecture reconstruction.[1] These limitations are fundamentally rooted in the architectural constraints of the models themselves: bounded context windows that cannot accommodate industrial-scale codebases, an acute sensitivity to the complex, non-linear structures of legacy code, and an inability to maintain coherent semantic understanding across tens of thousands of interdependent files.[1, 3]The research documented in ArchAgent: Scalable Legacy Software Architecture Recovery with LLMs (authored by Rusheng Pan, Bingcheng Mao, Tianyi Ma, and Zhenhua Ling from HiThink Research and the University of Science and Technology of China, accepted for publication at ICASSP 2026) addresses these specific, critical bottlenecks.[1, 2] The researchers introduce ArchAgent, a highly scalable, agent-based framework that intelligently combines static code analysis, adaptive code segmentation, and LLM-powered semantic synthesis to successfully reconstruct multiview, business-aligned architectures from vast, cross-repository codebases.[1, 2]2. Limitations of Classical Architecture RecoveryTo fully understand the technological leap represented by the ArchAgent framework, it is imperative to examine the historical trajectory of software architecture recovery methodologies and the fundamental limitations inherent in classical paradigms.2.1. Static and Dynamic Structural ExtractionClassical architecture recovery techniques operate almost exclusively in the structural domain. These methodologies function by employing static and dynamic analyzers to extract hard structural dependencies directly from the source code's Abstract Syntax Tree (AST) or its execution runtime.[1] The extracted dependencies typically include explicit function calls, module imports, class inheritance hierarchies, and variable data flow pathways.[1, 4] Once these atomic relationships are mapped into a massive dependency graph, classical algorithms apply various clustering heuristics to group these micro-entities into larger, macro-architectural components.[4]Prominent representative examples of these classical clustering approaches include the Algorithm for Comprehension-Driven Clustering (ACDC), Architectural Recovery using Concerns (ARC), and the Bunch clustering algorithm.[1, 4] While these traditional methodologies have proven effective for small-to-midsize projects that maintain strictly enforced structural boundaries, they exhibit critical points of failure when applied to massive, industrial-scale legacy systems.[3]2.2. Granularity Sensitivity and Semantic VoidsThe failure of classical techniques on legacy systems is driven by two primary limitations:Extreme Sensitivity to Input Granularity: Classical clustering algorithms are highly unstable; they produce vastly different, often contradictory architectural outputs depending on the specific level of granularity analyzed.[3] For instance, executing a clustering algorithm based on file-level dependencies will yield a fundamentally different system map than executing the exact same algorithm based on symbol-level or class-level dependencies. This instability makes it practically impossible to establish a definitive, ground-truth representation of the system's architecture without extensive manual tuning.The Absence of Semantic Context: Static analyzers are fundamentally blind to the actual purpose of the software. They mathematically process the syntax of the code but completely ignore the massive semantic wealth embedded within developer-defined code identifiers, inline comments, variable naming conventions, and version control commit histories.[3]Because modern legacy systems frequently implement critical business logic through nuanced, domain-specific conventions rather than strict, textbook structural hierarchies, the failure to capture semantic context renders the output of classical tools practically unusable.[3] The resulting diagrams are often "spaghetti graphs" that accurately map every single technical dependency but fail to convey any meaningful information regarding the actual business functions the software executes.[1] For practical industrial use, where accurate and maintainable architectural views are essential for system modernization, classical tools fall critically short.[3]3. The LLM Contextual Bottleneck in Software EngineeringWhile Large Language Models natively possess the semantic understanding that classical clustering tools lack, applying them directly to large-scale architecture recovery introduces a different set of profound computational bottlenecks.[1, 3] LLMs have demonstrated exceptional, human-level proficiency in micro-level tasks such as function-level code completion and bug detection.[3] However, industrial software is not written in single functions; it is distributed across massive repositories.Attempting to feed an entire industrial repository into an LLM is mathematically and computationally prohibited by the quadratic scaling complexity of the self-attention mechanism inherent in Transformer architectures. Even modern models equipped with extended context windows (e.g., 128k to 1M tokens) suffer from severe degradation in recall when processing massive documents. This phenomenon, frequently referred to as the "lost in the middle" effect, ensures that critical architectural relationships buried deep within the repository context are ignored, forgotten, or completely hallucinated during the synthesis phase.Furthermore, because legacy software frequently spans multiple interconnected repositories—comprising independent microservices, shared dependency libraries, and separate deployment configurations—the LLM must somehow maintain a coherent global state across highly heterogeneous codebases.[3] Standard generative approaches fail entirely at this cross-repository reasoning. ArchAgent resolves these deeply entrenched limitations by abandoning the brute-force monolithic prompt strategy in favor of a highly orchestrated, multi-agent pipeline designed specifically for scalable codebase comprehension.[2, 5]4. 4.1. Reference Indexing and Functionally-Aware SummarizationThe architectural recovery process initiates at the lowest micro-level. Before the system can infer global architecture, it must first understand the isolated purpose of each individual file and how that file interacts with the rest of the software ecosystem. To achieve this, the File Summarizer agent conducts rigorous static code search and builds a comprehensive reference index to mathematically establish cross-file relationships.[3]During this deterministic phase, the framework maps exactly how subjects (files, classes, or specific functions) are referenced by other subjects within the repository, and conversely, what external subjects they invoke (e.g., subject x referenced by: [subj 1, subj 2...], referencing: [subj 1, subj 2...]).[3]Following the construction of the reference index, the LLM is deployed to generate a concise semantic summary for each file. Crucially, the File Summarizer does not operate in a vacuum; it explicitly utilizes the reference index to pull in functionally related files to serve as auxiliary context.[1] By injecting a target file's direct dependencies into the LLM prompt, the model is required to identify other files that are functionally closely related before generating the target file's summary.[1] This ensures that the resulting summary captures not just the file's isolated, internal mechanics, but its precise role and interrelated responsibilities within the broader execution chain, massively improving functional awareness across the repository.[1]4.2. Repo Manager and the Mathematics of Adaptive GroupingOnce the entire legacy repository is reduced to a massive collection of semantically enriched file summaries, the framework must feed this data into the LLM to generate higher-level architectural abstractions. However, a fundamental issue remains: even the condensed summaries of a 10,000-file repository will drastically exceed a standard LLM's maximum context window.[4]Traditional approaches to this context-overflow problem rely on naive, fixed-size chunking strategies. A repository is blindly sliced into sequential blocks of a predetermined size (e.g., 8,000 tokens per block). This rigid strategy inevitably results in highly imbalanced data distributions. Specifically, it almost always creates an isolated "tail group" at the very end of the partition containing only a fraction of the token limit.[3] When the LLM processes this micro-group, the acute lack of sufficient surrounding context triggers severe hallucination, sub-optimal summarization, and a complete failure to detect architectural boundaries, destroying the fidelity of those specific modules.[3]To eradicate this structural inefficiency, ArchAgent introduces an innovative Adaptive Grouping algorithm, orchestrated by the Repo Manager.[3] This dynamic mechanism ensures perfectly uniform group sizes by mathematically adjusting the partition strategy based on the specific token density of the repository being analyzed.[3]The adaptive grouping algorithm operates via the following mathematical sequence:First, the system calculates the total token count, mathematically denoted as $T$, for the entire concatenated repository summary.[3, 4]Next, the system defines a maximum token threshold, denoted as $M$. This threshold represents the absolute upper limit of tokens per model input, strictly constrained by the underlying LLM's defined context window capabilities.[3, 4]Finally, the repository is dynamically partitioned into a specific number of groups, denoted as $G$, defined by the formula:$$G = \lceil T / M \rceil$$where the $\lceil \cdot \rceil$ notation denotes the mathematical ceiling function.[3, 4]By forcing the total token count to be divided by an integer number of groups (ensured by the ceiling function), the algorithm guarantees that the token payload is distributed in segments that are as close to the mathematical average as possible.[3, 4] This calculation completely prevents the formation of undersized tail groups, minimizes the variance in group sizes, and ensures that every single execution of the LLM receives a maximum, balanced contextual payload.[3, 4] Furthermore, to ensure group independence and minimize inter-group correlation loss, the algorithm groups semantically adjacent files together during the partitioning phase.[3]4.3. Scalable Diagram Generation via Mermaid SyntaxThe final operational stage of the ArchAgent pipeline is executed by the Architect agent. The primary function of the Architect is to translate the dense semantic insights generated by the Readme Generator into visual, human-readable architectural diagrams.[2, 3]Because attempting to render a monolithic, highly detailed diagram for a massive repository in a single generative pass is highly error-prone and visually incomprehensible, the Architect utilizes a strategy of contextual pruning.[2] It first generates partial, isolated sub-system architecture diagrams representing distinct domains of the software.[3] These modular representations are mathematically encoded using Mermaid flowchart grammar.[3] Mermaid is a text-based diagramming syntax that is natively highly compatible with LLM output generation, as it relies on simple Markdown-like text declarations rather than complex graphical rendering engines.[5]Once the partial sub-architectures are fully generated and validated against the repository summaries, the Architect merges the disparate Mermaid graphs into a cohesive, multiview, system-level architecture diagram.[5] This multiview paradigm is critical; it ensures that human stakeholders can inspect the legacy system from multiple levels of abstraction—ranging from high-level cross-service data flow down to low-level intra-component interactions—without suffering from visual clutter or information overload.[2, 5]5. Experimental Design and Human Evaluation ProtocolDue to the inherent subjectivity and high level of abstraction required in architectural representations, purely automated evaluation metrics (such as n-gram overlap or BLEU scores) are fundamentally insufficient for evaluating the quality of generated architecture diagrams.[6] To ensure a highly reliable, scientifically valid, and unbiased assessment of ArchAgent's outputs, the researchers designed a rigorous human-in-the-loop evaluation protocol.[1]6.1. Participant Selection and Cohort DesignThe evaluation process leveraged a specialized panel of 30 senior software engineers sourced from diverse industrial company departments.[1] Stringent pre-screening criteria were strictly enforced: every participant was required to possess a minimum of five years of professional software development experience and be actively responsible for independently maintaining at least one highly complex, production-level code repository.[1] This screening ensured that the evaluators possessed the deep domain expertise and cognitive frameworks necessary to accurately interpret and critique highly abstract system diagrams.To neutralize systematic bias, mitigate learning effects, and prevent participant fatigue from skewing the results, the cohort of 30 engineers was divided into two counterbalanced groups utilizing a strict within-subjects experimental design [1]:Group A ($n=15$): Evaluated the output of the baseline tool (DeepWiki) first, followed by the output generated by ArchAgent.[1]Group B ($n=15$): Evaluated the output of ArchAgent first, followed by the output from DeepWiki.[1]Mandatory, timed breaks were strictly enforced between evaluation sessions to maintain the cognitive acuity of the participants.[1]6.2. Evaluation Protocol and Metric FormulationDuring the experiment, each senior engineer was tasked with assessing a total of 16 architecture diagrams (calculated as 8 ArchEval benchmark repositories evaluated across the 2 distinct generative systems).[1]For every single model-generated diagram, the evaluator was provided with a comprehensive assessment package: the official ground-truth architecture document (from ArchEval), the AI-generated architecture diagram, and a highly structured evaluation matrix table.[1] This evaluation matrix geometrically decomposed the architecture into granular, testable categories: architectural layers, functional nodes, and relational edges (the specific interactions and connections between nodes).[1]The evaluators rigorously verified each generated element within the matrix, applying binary "true" or "false" designations. Crucially, they were also required to manually identify and append any critical architectural components that were present in the ground truth but that the AI had omitted.[1]This meticulous, node-by-node manual verification allowed the research team to aggregate mathematically precise counts of:True Positives (TP): Architecturally valid nodes and edges successfully identified and generated by the model.False Positives (FP): Hallucinated, incorrect, or architecturally irrelevant components generated by the model.False Negatives (FN): Critical architectural components that exist in the ground truth but were missed by the model.[1]From these base empirical counts, standard information retrieval metrics were computed to definitively quantify performance: Precision ($P$), Recall ($R$), and their harmonic mean, the $F_1$ Score ($F_1$).[1, 3]7. Ablation Studies: The Criticality of Contextual DependencyTo empirically validate the specific structural decisions made during the architectural design of the ArchAgent pipeline, the research team conducted an exhaustive ablation study focused specifically on the role of contextual dependency.[2, 4] Ablation studies operate by systematically removing, degrading, or disabling specific components of a framework to accurately measure their isolated, individual impact on the overall performance of the system.The central hypothesis tested in this ablation study posited that integrating broad, cross-repository context—specifically, cross-file dependencies extracted by the File Summarizer and external DevOps signals ingested by the Readme Generator—is the primary driving mechanism for enhancing the precision of the generated architecture diagrams, especially when attempting to reconstruct the business logic of production-level repositories.[3]To test this, the researchers disabled the reference indexing module within the File Summarizer, isolating files during the LLM summarization phase, and restricted the Readme Generator from accessing any cross-repository DevOps signals (such as QPS metrics and API routing configurations).[2, 3, 4]The results were immediate and severe: researchers observed a sharp degradation in the accuracy and usefulness of the generated architectures.[2, 3, 4] Without this critical contextual scaffolding, the LLM defaulted to generating highly localized, strictly structural diagrams that closely resembled the flawed output of classical tools like ACDC or Bunch.[1] The generated nodes and structural edges were technically correct at the isolated file level, but the overarching business logic—the true, functional "architecture" of a production-level system—was entirely lost.[3, 4]This ablation mathematically confirms that dependency context is not merely an incremental enhancement or a minor optimization; it is the fundamental, critical mechanism that allows an LLM to elevate its reasoning capabilities from simple code comprehension to highly accurate, business-aligned architectural recovery.[2, 4] The consistent effects observed across different repositories solidify the necessity of cross-repository contextual awareness in modern software analysis.[3]9. Real-World Case Studies and Industrial ApplicationMoving beyond the highly controlled, scientific environment of the ArchEval Benchmark, the practical, real-world efficacy of the ArchAgent framework was conclusively demonstrated through a complex industrial case study. This case study involved the recovery of critical business logic from a deeply entrenched, actively deployed legacy project—specifically, an industrial-scale SQL transformation codebase.[1]In this live industrial deployment, the software had accumulated years of undocumented patches, hotfixes, and structural deviations, resulting in severe architectural drift.[1, 2] By deploying ArchAgent against this codebase, the framework successfully mapped the critical entry points of the SQL execution engine.[2] Utilizing the logic defined in Algorithm 1, the system traced the downstream data transformations, aggregated the relevant internal APIs, and produced a multiview, Mermaid-encoded architecture diagram.[1, 4, 5]This generated architecture successfully isolated the core, critical business behaviors of the SQL engine from the surrounding decades of technical debt.[1, 4] It provided the engineering team with an accurate, human-readable map of a system that was previously considered too complex to fully comprehend, proving the immediate commercial viability of the ArchAgent framework.[1, 2]10. Implications for Software Engineering and DevOpsThe implications of this breakthrough technology extend far beyond the mere automation of software documentation. The proven ability to autonomously extract highly accurate, mathematically stable ($F_1 = 0.966$), and business-aligned architectural diagrams from massive legacy codebases unlocks entirely new paradigms for software engineering and systems maintenance.[1, 3]Accelerated Legacy Modernization and Cloud Migration: Organizations attempting to migrate monolithic legacy applications to modern, distributed microservice architectures frequently experience catastrophic failure. These failures occur because the exact boundaries of the existing business logic are unknown, hidden beneath layers of architectural drift. ArchAgent provides an accurate, empirically verified map of the current system state, allowing enterprise architects to plan precise extraction points and service boundaries without risking regressions.[2, 4]Continuous Architecture Validation within CI/CD: By integrating the ArchAgent framework directly into Continuous Integration/Continuous Deployment (CI/CD) pipelines, engineering teams can continuously monitor and police architectural drift. As developers merge new code into the repository, the system can autonomously regenerate the architecture in real-time, instantly flagging pull requests that violate intended design boundaries, effectively enforcing architectural compliance at the compilation level.[7]Cross-Repository Ecosystem Mapping: Modern software systems are rarely confined to a single, isolated repository. They operate as vast ecosystems of interacting microservices. ArchAgent's unique ability to synthesize cross-repository signals and trace cross-boundary API executions means it can map the interactions of entire corporate ecosystems, revealing hidden dependencies, unoptimized data flows, and critical security bottlenecks that are fundamentally invisible to traditional, single-repo static analyzers.[1, 2]11. ConclusionThe recovery of accurate, reliable, and usable software architecture from massive legacy software systems has long been a seemingly insurmountable challenge, obstructed by the continuous erosion of code structure and the inherent, fundamental limitations of both classical static analyzers and modern Large Language Models.[1, 2] Classical, deterministic tools fail utterly to capture the semantic reality of business logic, while semantic LLMs collapse under the massive contextual weight of industrial-scale code repositories.[1]The ArchAgent framework fundamentally resolves this long-standing technological dichotomy.[1, 2] By engineering an intricately orchestrated, multi-agent pipeline, the framework successfully domesticates the raw power of LLMs for repository-scale operations. The introduction of the mathematical Adaptive Grouping algorithm completely mitigates the context-window limitations that have historically plagued standard generative approaches, ensuring perfectly stable and scalable code segmentation without any contextual data loss.[2, 3] Concurrently, the sophisticated fusion of deterministic static reference indexing with cross-repository DevOps heuristics—formalized in Algorithm 1—allows the system to synthesize multi-view diagrams that are not just structurally accurate at the syntax level, but deeply and fundamentally aligned with the real-world execution of the business.[1]Rigorous empirical evaluation against the newly established ArchEval Benchmark—spanning tens of thousands of files and millions of lines of code across highly diverse programming languages—demonstrates that ArchAgent achieves unprecedented, state-of-the-art accuracy. Yielding an average $F_1$ score of 0.966, the framework vastly outperforms existing industrial baselines with undeniable statistical significance.[1, 3] Supported by conclusive ablation studies that formally affirm the absolute necessity of dependency context, ArchAgent stands as a transformative methodology in the field of software engineering. It provides the necessary, scalable tools to illuminate, understand, and ultimately modernize the opaque legacy systems that currently power global digital infrastructure.[1, 2, 3]
