# Repository Knowledge Graph System (Postgres + pgvector)

## Purpose

This project builds a **repository knowledge system** that extracts
information from a software codebase and stores structured artifacts so
that an AI agent can understand the **business functionality** of a
company by analyzing its code.

The system should: 1. Parse a repository and extract structural
relationships (imports, calls, dependencies). 2. Generate summaries
describing what each file/module does. 3. Store both the **semantic
meaning (text)** and the **structural connections (graph edges)**. 4.
Allow an agent to retrieve relevant information and understand how
different modules relate to business capabilities.

This system is inspired by the *ArchAgent* paper, which demonstrates
that combining **dependency graphs + summaries** significantly improves
architectural understanding.

------------------------------------------------------------------------

# High Level Architecture

The system has four layers:

1.  **Repository Parsing**
2.  **Knowledge Storage**
3.  **Embedding + Retrieval**
4.  **Agent Context Construction**

We will use **Postgres with pgvector** so that we can support both: -
structured graph queries - semantic search for summaries

------------------------------------------------------------------------

# Data Pipeline

## Step 1 --- Repository Analysis

Input: repository path

Process: - Discover source files - Parse AST - Extract dependencies

Outputs: - subjects (files/classes/functions) - edges (dependencies) -
summaries

Example artifact:

``` json
{
  "client/index.tsx": {
    "overall_summary": "...",
    "file_cluster": [...],
    "important_relationships": [...],
    "group_function": "..."
  }
}
```

# Database Schema

## 1. Repository Runs

Each analysis run of a repo is stored independently.

``` sql
create table repo_runs (
  id uuid primary key,
  version int not null,
  repo_address text not null,
  fingerprint text not null unique,
  generated_at timestamptz not null,
  meta jsonb default '{}'
);
```

Purpose: - version analysis runs - enable diffing across runs

------------------------------------------------------------------------

## 2. Subjects

A subject is a code entity.

Examples: - file - class - function

``` sql
create type ref_subject_type as enum ('file','class','func');

create table repo_subjects (
  id uuid primary key,
  repo_address text not null,
  subject_path text not null,
  subject_type ref_subject_type not null,
  language text,
  is_entrypoint boolean,
  created_at timestamptz default now(),
  unique (repo_address, subject_path, subject_type)
);
```

Example:

  subject_path          subject_type
  --------------------- --------------
  server.ts             file
  ChatStore             class
  writeContextSummary   func

------------------------------------------------------------------------

## 3. Summaries

Each subject has a summary generated by the analysis pipeline.

``` sql
create table repo_summaries (
  run_id uuid references repo_runs(id),
  subject_id uuid references repo_subjects(id),
  overall_summary text not null,
  group_function text,
  file_cluster jsonb,
  important_relationships jsonb,
  raw_output text,
  updated_at timestamptz,
  primary key (run_id, subject_id)
);
```

Purpose: - describe the function of each file/module - provide semantic
context for the agent

------------------------------------------------------------------------

## 4. Dependency Edges

Represents the structural connections between subjects.

``` sql
create table repo_edges (
  run_id uuid references repo_runs(id),
  from_subject_id uuid references repo_subjects(id),
  to_subject_id uuid references repo_subjects(id),
  edge_type text default 'ref',
  primary key (run_id, from_subject_id, to_subject_id, edge_type)
);
```

Examples:

  from            to              type
  --------------- --------------- --------
  server.ts       chat-store.ts   import
  chat-store.ts   types.ts        import

These edges form a **dependency graph**.

------------------------------------------------------------------------

# Embedding Layer (pgvector)

To support semantic retrieval we store embeddings for summaries.

``` sql
create table repo_embeddings (
  run_id uuid,
  subject_id uuid,
  kind text,
  text_for_embedding text,
  embedding vector(1536),
  primary key (run_id, subject_id, kind)
);
```

Typical embedding text:

    subject_path
    overall_summary
    group_function

Example:

    server/chat-store.ts
    Manages chat sessions and message persistence
    Provides CRUD operations and disk persistence

------------------------------------------------------------------------

# Index for Vector Search

``` sql
create index repo_embeddings_ivfflat
on repo_embeddings
using ivfflat (embedding vector_cosine_ops)
with (lists = 100);
```

# Core Queries

## Query 1 --- Semantic Retrieval

Find relevant files for a question.

``` sql
select
  s.subject_path,
  sum.overall_summary,
  1 - (e.embedding <=> $query_embedding) as score
from repo_embeddings e
join repo_subjects s on s.id = e.subject_id
join repo_summaries sum on sum.run_id = e.run_id and sum.subject_id = e.subject_id
order by e.embedding <=> $query_embedding
limit 12;
```

------------------------------------------------------------------------

## Query 2 --- Graph Expansion

Find connected modules.

``` sql
select distinct s2.subject_path
from repo_edges e
join repo_subjects s1 on s1.id = e.from_subject_id
join repo_subjects s2 on s2.id = e.to_subject_id
where s1.subject_path = $file;
```

------------------------------------------------------------------------

## Query 3 --- Core Modules

Identify central components of the architecture.

``` sql
select s.subject_path, count(*) as inbound_refs
from repo_edges e
join repo_subjects s on s.id = e.to_subject_id
group by s.subject_path
order by inbound_refs desc
limit 20;
```

These usually correspond to: - core services - shared infrastructure
modules

# Agent Context Construction

When an agent receives a question:

1.  Convert the query to an embedding
2.  Retrieve top summaries via vector search
3.  Expand neighbors via dependency graph
4.  Assemble a context pack

Example context pack:

    Top modules:
    - server/chat-store.ts
    - server/server.ts
    - reference-graph.ts

    Summaries:
    ...

    Key dependencies:
    server.ts → chat-store.ts
    server.ts → repo-cost-ledger.ts

This allows the agent to reason about: - architecture - dependencies -
business functionality

# Summary

This system combines:

-   **Graph structure** (repo_edges)
-   **Semantic summaries** (repo_summaries)
-   **Vector retrieval** (pgvector)
-   **Run versioning** (repo_runs)

to build a **knowledge graph of a software system**.

The final goal is to provide **high quality architectural and business
context** to AI agents so they can reason about how a company's software
implements its business processes.
